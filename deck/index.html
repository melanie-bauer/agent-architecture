Where does collaboration between agents genuinely help,

and where are we building a slow, expensive prompt conference?

The first problem, several specialists, comes with the question from the title of this session. Where does collaboration between agents really help, and where are we building a slow, expensive prompt conference? A prompt conference is four agents in a room: same model, same tools, same data, different hats. It looks like teamwork and it costs like teamwork, but most of it is theatre. I'll give you my answer at the end. To get there, we need three basics.

An agent is a loop with a budget

The model picks a step, code runs it, the result goes back. This repeats until the model is done or the budget runs out.

Basic one: what an agent is. An agent is a loop. Follow the line clockwise. A task comes in. One: the model looks at the task and everything it knows so far and picks the next step, usually a tool call. Two: code runs that tool. The model never touches anything itself. Three: the result goes back into the context. Four: before the next round, the budget is checked: steps, tokens, time. If there's budget left, the model picks again. When the model is done, the answer leaves the loop at the top. Two things matter for everything that follows. The model decides, but code executes: that's where we'll put our boundaries. And a loop without a budget isn't autonomy. It's a bill. So who decides what happens next, the model or you?

Who decides the next step?

Each station to the right adds flexibility and makes the system harder to predict, test and debug.

That's basic two, the control ladder. The question is always: who decides the next step? Code: you decide. A workflow: a graph decides, with steps, branches and pauses. A single agent: the model picks tools. Centralized: a supervisor agent picks other agents. Decentralized: peers pick each other, nobody is in charge. Each station to the right buys flexibility, and you pay with predictability, testability and debugging time. So climb only for the parts of your problem where the path is really unknown. Usually that's a small part. And as soon as an agent talks to anything outside its loop, it needs a wire.

Three wires, three protocols

We’ll meet each of them on the way.

Basic three: the wires. An agent connects to three kinds of things, and each connection now has an open protocol. MCP, the Model Context Protocol, connects an agent to tools and data. Anthropic published it at the end of 2024. A2A, the Agent2Agent protocol, connects an agent to another agent it does not control. Google started it in April 2025, it's now a Linux Foundation project, and version 1.0 is out. AG-UI, the Agent User Interaction protocol, connects the agent system to the user interface: streaming text, tool calls, state and approvals. It comes from CopilotKit. We'll meet A2A in chapter one, MCP in chapter three and AG-UI in chapter four. If you're on .NET: Microsoft Agent Framework supports all three. That's enough basics. Chapter one.

Several specialists

When is a second agent worth it, and which shape should the agents have?

Chapter one: several specialists. When is a second agent worth it, and which shape should a team of agents have? To make it concrete, I'll use an agent system that plans a developer conference. Seven areas with their own data: program, venue, catering, travel, budget, marketing and accessibility. You'll see it live at the end. For chapters two to four there's a second example, an incident desk, and I'll show it right where it fits. But before we build a team, let's see how far one agent gets.

The workflow fits known paths: extraction, triage, approvals. Predictable, testable, cheap. It gets stuck when the path is really unknown. The agent with tools fits one domain where you don't know the path in advance. It gets worse with many tools and unrelated domains. The agent with skills fits many capabilities with one owner. If that decision reminds you of something, it should.

Monolith or microservices?

One agent is a monolith, a network is microservices. Same rule: monolith first.

Worse than microservices: every hop is a model call, and the contract between agents is plain language.

You already know this decision. A single agent is a monolith: all tools, all data, one context. A network of agents is microservices. And the rule we learned there applies here too: monolith first. Split when there's a reason, along a boundary, and the reasons are almost the same as for services. Different data, that's a bounded context. Different permissions, a different model, a different clock. The costs are the same too: network hops, distributed debugging, data that's out of date. And one thing is worse than with microservices: every hop is a model call, slower, more expensive and not deterministic. And the contract between agents is plain language, so every handoff is a translation. A network without a real reason to split is a distributed monolith. With agents, we call that a prompt conference. So here are the reasons to split.

When one agent no longer passes your evals, because the context gets too big, the permissions clash or the costs explode, you split, and then along one of these four lines. It's my rule, not a law of nature, but it has held up well for me. Context: they need different data, or simply less. In our conference, travel sees passports, and nobody else should. Capabilities: they may do different things. The agent that reads untrusted input should not hold the delete button. Cost: they need a different model. Clock: they run in parallel, or for hours. Waiting for a human is no reason for a second agent, though. That's a workflow that pauses, chapter two. What's not on the list: a different persona. If two agents differ only in their system prompt, they're one agent in two costumes. So say you have a real reason to split. Which shape should the team have?

Centralized, with our conference team. One supervisor splits the request, delegates to the specialists and merges the answers. In Mastra that's an agent with an agents property. Good for one team that owns one answer.

Strengths

Centralized is good for one team that owns one answer. Strengths: policies, budgets and the final answer live in one place, the supervisor can ask specialists in parallel, and the trace is one tree. Weaknesses: the supervisor is a bottleneck. When accessibility finds a problem with a room, the supervisor has to relay it to venue, and it can retell it wrong. If it misunderstands something, everything after it is wrong. So what happens if we take the supervisor away?

Decentralized

No supervisor. Each peer decides whom to ask.

Ownership can move from one agent to the next. That’s a handoff.

Then you get decentralized. No supervisor. Each peer decides itself whom to ask. Venue asks accessibility directly, catering asks budget directly. In LangGraph that's a swarm, elsewhere handoffs or peer to peer. And ownership can move: in a handoff, the next agent takes over the conversation.

Decentralized

Good for work where each step decides who is next.

Strengths

  • No bottleneck
  • The expert answers directly
  • Ownership can move

Weaknesses

  • Nothing stops it by default
  • Agents can loop
  • Hard to trace

Needs hard limits in code: max depth, max messages.

Decentralized is good for work where each step decides who is next, so no single agent can plan it up front. Strengths: no bottleneck, the expert answers directly, ownership can move. Weaknesses: who stops it? Who owns the final answer? Agents can ping-pong forever, and debugging a conversation nobody planned is hard. So it needs hard limits in code: maximum depth and maximum messages per request. In the demo that's three levels and twelve messages. Before the other shapes, one distinction that decides a lot.

Agent as a tool, or handoff?

Who owns the answer after the call?

Between centralized and decentralized there's one question that decides a lot: after the call, who owns the answer? Agent as a tool: the caller calls another agent like any other tool and gets a result back. It stays in charge, and it answers the user. That's what a supervisor does. In Mastra you give an agent other agents, in Microsoft Agent Framework you turn an agent into a function, and a remote A2A agent can be a tool just as well. Handoff: the agent passes the conversation on. From now on the next agent talks to the user. That's decentralized. Rule of thumb: if you need one place for policy and the final answer, use agents as tools. Hand off only when the next agent should really own the conversation, like a support desk passing you on to billing. Three more shapes, briefly.

Hierarchical: centralized, repeated, teams with their own leads. Every level adds latency. Blackboard: peers write one shared artefact, like our conference plan. Watch for stale reads, you'll see one in the demo. Council: several answer, one combines. It only helps if the members really differ. Which brings us to the prompt conference.

Council or prompt conference?

Both have the same shape. Only the members differ.

Both boxes have the same shape: four members answer the same question, one step combines. On the left, a real council: different models, or members that look at different data. Their answers can disagree, and that's how they catch each other's mistakes. On the right, the prompt conference: SRE, security, performance, product. Four personas, same model, same tools, same data. They agree because they're the same, not because they checked. Research on debate agrees: a 2025 study by Zhang and colleagues tested five debate methods on nine benchmarks. Debate often did not beat simply asking once with reasoning, or asking several times and voting. What did help: members built on different models. Before the evidence, a quick look at the wire that connects agents across teams and companies: A2A.

How A2A works

Read the card, send a message, follow the task.

How does that work in practice? Three steps. Discovery: every A2A agent publishes an agent card, by default at a well-known URL, slash well-known slash agent-card.json. It says who the agent is, which skills it has, with descriptions and examples, which endpoints and protocol bindings it speaks, JSON-RPC, gRPC or plain HTTP, whether it streams, and how you authenticate. You can also get cards from a registry or simply configure them. The description in the card is what a supervisor reads to decide whom to call. So the card is your API documentation, written for a model. Then you send a message. The agent can answer right away, or it creates a task with an id and a lifecycle: working, then completed, failed, canceled or rejected. Or interrupted: input required, or auth required. That's the A2A version of pause: the remote agent needs something before it can go on. Results come back as artifacts, documents or structured data. You stream them with server-sent events, get a webhook, or poll. What you never see: its tools, its prompt, its memory. The venue company runs its agent with its own model and its own data, and you only see the contract. Version 1.0 has been out since April, and Microsoft Agent Framework and Mastra both host and call A2A agents.

A2A works with every topology

A2A is a wire. Who owns the answer is a separate question.

And one misunderstanding: A2A means decentralized? It doesn't. A2A is a wire, and it works with every topology. On the left, remote A2A agents are simply tools of the supervisor, maybe run by the venue and the caterer. On the right, peers call each other over A2A. Who owns the answer and who owns the agents are two separate questions. One tip from the demo: check what your card publishes. In my Mastra version it contained the agent's full instructions. The biggest study is from Google Research, MIT and others, updated this April: 260 configurations, six agent benchmarks, one single agent against four team architectures, with models from OpenAI, Google and Anthropic. On a task that splits into parallel parts, financial analysis, a centralized team was 81 % better than one agent. On a task where each step depends on the one before, planning in a game world, every team variant was worse, by up to 70 %. And once one agent already reaches about 45 % accuracy, more agents tend to hurt. Without a supervisor that checks, errors were amplified 17 times, with one about 4 times. Stanford, April: give one agent and a team the same thinking budget, and the single agent is as good or better on multi-hop questions. A lot of what we credit to teams is just more compute. Anthropic, January: start with one agent. Teams help with polluted context, parallel work and specialisation, and cost three to ten times the tokens. That's the four C's again. And it's why my default is one agent until it fails your evals.

Which architecture when?

So how do you choose? Read it like a line map, left to right. Is the path known? Then a workflow, with LLM steps where you need language understanding. Does one agent pass your evals? Then a single agent, the cheapest option. If it has many tools, give it skills before you give it colleagues. If not, split along the four C's. Is there one owner of the answer? Then centralized, hierarchical if it gets large. If no single agent can own the answer, because each step decides who works next: do the agents talk, or build one artefact? Talk: decentralized, with limits. Artefact: blackboard. A council can be added at any station when you need independent judgement, but only with different models or different evidence. That's chapter one. But even the best shape breaks when a task takes longer than one conversation.

Tasks run longer

What happens when a task takes hours or days, and what should an agent remember?

Chapter two: tasks run longer. An outage where the fix waits for someone to approve it. A conference plan that grows over weeks. A chat loop can't do that, and it shouldn't try.

Put a workflow around the agent

Fixed steps in code. An agent only where the path is open.

The first answer: put a workflow around the agent. This is the incident desk you'll see in a minute: checkout returns errors, a ticket comes in. Loading the ticket is code, and it already removes the customer's name, e-mail and card. Classifying the severity is one LLM step with a small model. A low severity ticket takes the other branch: a backlog item, done. Only the investigation is open, so that's where the agent works, with two read-only specialists. Then a person approves, and plain code executes, against an allow list. That's the control ladder applied: each step only as flexible as it needs to be. And a workflow can do something a chat loop can't: wait.

Pause, and resume days later

The workflow stops at the approval and stores its state. Nothing waits in memory.

On Monday the investigation is done and the workflow reaches the approval. It stops and writes a snapshot of its state into the database. The process can restart, you can deploy a new version. On Wednesday a person approves, the workflow loads the snapshot and continues where it stopped. In Mastra that's suspend and resume, with the snapshot in the storage you configure. In Microsoft Agent Framework it's request ports and checkpoints. Durable state is what makes long tasks robust. Let me show you that live. Memory: what an agent keeps

Message history

the last messages of this conversation

per thread

per user or project

Back to the slides. The workflow keeps the state of one run. But over weeks, an agent also has to remember things. Most frameworks offer the same four kinds of memory. These are Mastra's. Message history: the last messages of the current conversation, per thread. Working memory: structured facts and decisions, like "the budget cap is 180,000" or "Room C is out", kept per user or per project across conversations. Semantic recall: older messages found by meaning. And compression: older messages condensed into notes so the context stays small. Mastra calls that observational memory. The important part for architecture: everything you remember ends up in the context of some model call. So memory is a Context decision, and a privacy decision. And in a network that raises a question: who may remember what?

Who may remember what?

  • Specialists start with an empty threadthey get the delegation prompt, not the whole conversation
  • Save results, not transcriptsstructured findings and decisions, in working memory
  • Shared memory is shared statethe same risks as a blackboard: conflicting writes, stale reads
  • Personal data stays where it is neededwhat one agent remembers can leak into another agent’s context
In Mastra, every delegation starts the specialist with a new, empty thread. It gets the delegation prompt, and only the prompt and the answer are saved. That's a good default. Save results, not transcripts: decisions and structured findings go into working memory, not the whole chat. Shared memory is shared state, with the same risks as a blackboard. And personal data stays where it's needed. If the travel agent remembers passport numbers, they must not end up in the budget agent's context. Memory decides what an agent knows. Chapter three is about what it can do.

Tools become risky

How do you keep an agent from doing what it should not do?

Chapter three: tools become risky. A prompt can ask an agent to be careful. Only the architecture can make sure. We start with the simplest boundary.

Each agent gets only its own tools

The smallest tool set that does the job. That includes tools from MCP servers.

Each agent gets only its own tools. Venue can list, assign and drop rooms. Travel reads passports and books travel. Budget reads the budget and checks the plan. Nobody else holds those tools, so nobody else sees a passport number. That includes MCP. An MCP server often brings forty tools. Don't hand the whole server to every agent. Filter per agent: budget gets exactly the one tool it needs. Fewer tools also means a smaller context and fewer wrong choices. And the tools an agent does get, sort them by what they can break.

Sort every tool by what it can break

  • Readwatch what comes back: untrusted text, customer data
  • Reversible writerestart, rollback, feature flag: approval for the exact arguments
  • Irreversiblerefund, delete, signed contract, public post: approval, only on the agent that talks to the person

Behind every tool: credentials for exactly this one job.

Read tools are the least dangerous, but watch what comes back: untrusted text and customer data. Reversible writes, like restart, rollback or a feature flag, need a person, and the approval is bound to the exact arguments the person saw. Irreversible tools, a refund, a delete, a signed contract, a public post, get an approval and live only on the agent that talks to the person. An approval request from deep inside a delegation is hard to explain to whoever has to click. And behind every tool: credentials that can do exactly this and nothing more. That's the boundary that holds when everything else fails. Read tools sound harmless. They aren't.

Text from outside can give orders

Prompt injection. Let the agent that reads it hold no write tools.

Everything a tool returns goes into the context, and the model can't reliably tell data from instructions. A talk abstract, a support mail, a log line can say "ignore all previous instructions". That's prompt injection. You won't filter it away reliably. So limit what it can reach: the agent that reads untrusted text holds only read tools. It hands over findings in fixed fields, not free text. The agent with write tools never sees the original text, and its writes still need approval. That's the Capabilities C in practice. The incident desk has exactly this case: a log line with an injection in it. And findings in fixed fields is already a rule for handoffs.

What crosses a handoff

If the next agent needs the whole chat history to do its job, the split is in the wrong place.

Every edge in a network is a handoff, and that's where systems leak. In the incident desk, the supervisor happily copied the customer's e-mail address into the delegation prompt. You'll see the filter that catches it in a few minutes. So at every handoff: filter what the next agent may see. Enforce limits on depth and messages in code. And fail closed: if your filter throws, the delegation must fail, not continue unfiltered. In Mastra that's a setting you have to change. And if the next agent needs the whole chat history, you split in the wrong place. Hand over structured findings instead. Tools are bounded now. But some decisions shouldn't be made by any agent.

Users intervene

How does a person stay in control without watching every step?

Chapter four: users intervene. They want to approve, correct, or say no. How does a person stay in control without watching every step? Two parts: the wire to the person, and the screen.

AG-UI: events to the user

The UI reacts to typed events. A run can stop and ask a person. The answer starts a new run.

AG-UI is the wire from the agent system to the person. About thirty typed events: a run starts, text streams, tool calls stream their arguments, sub-agents start and finish, state is synced. The one that matters most: a run can end with an interrupt. I need a human decision. The UI shows a card, a person approves or rejects with a reason, and the answer starts run 2, which resumes where the agent stopped. Nothing waits in memory in between. That's the pause and resume from chapter two. AG-UI only carries the question to the UI and the answer back. CopilotKit is built on it, and the incident desk chat speaks it. AG-UI gets the question onto the screen. What should the screen show?

An approval is a user interface

  • Show the exact argumentsand bind the approval to them
  • Show the evidenceand not only the action
  • A “no” needs a reasonand the agent has to receive it
  • The approver is a person with a rolesigned in and logged, and approvals expire
  • Generative UI: the agent picks, the app renderscomponents from your catalogue, never its own HTML
Human in the loop is usually drawn as a little box saying "human". In reality it's a user interface, and a hard one. Show the exact arguments and bind the approval to them: if the arguments change after I clicked yes, my yes doesn't count. Show the evidence, not only the action. A "no" needs a reason, and the agent must actually receive it. In my stack the reason got lost on the way, and I had to fix it in the UI. The approver is a signed-in person with a role, every decision is logged, and approvals expire. And don't ask people things they can't judge. That only trains them to click yes. The approval card is one example of generative UI. Instead of text, the agent picks a component, a room plan, a budget bar, this card, and the app renders it. The agent decides what to show, the app decides how. It never gets to send its own HTML. That's a capability boundary again. Let's see chapters three and four together, with the incident commander. Does it work?

Four problems, four answers on paper. Now: how do you see what really happens, find a bug, and keep it fixed?

Back to the slides. Four problems, four answers, and you've seen most of them work. The abstract promised you design, test and debug. So the last part: how do you see what really happens in a system like this, how do you find a bug, and how do you keep it fixed?

Every run is a tree you can read

Each model call, tool call, handoff and approval is a span, with its input, output, tokens and time.

Observability for agents means tracing. Every run becomes a tree of spans: each model call, each tool call, each delegation or A2A call, each approval, with input, output, tokens and time. This is a decentralized run from the conference planner. You'll see it live at the end. Venue puts the Agents track into Room C and posts the venue cost, 44,200 euros. Then venue asks accessibility, and Room C turns out not to be step-free. Meanwhile the budget peer reads the board, and it reads 44,200, the old value. Venue drops Room C later, and the real cost is 38,600. Without the trace you'd only see a wrong total. In Mastra the traces show up in Studio. With OpenTelemetry you can send them to any tool you already use, and Microsoft Agent Framework emits OpenTelemetry too. So how do you get from a trace to a fix?

Debugging an agent system

Ask the trace

Who saw what?

Which tools were offered?

Why did it delegate?

How did it stop?

Then

Find the first wrong span

Replay the run with the recorded or a scripted model

Fix the boundary, not the prompt

Add a test so it stays fixed

I ask the trace four questions. Who saw what: what was in the context of the call that went wrong? Which tools were offered? Why did it delegate, and to whom? And how did it stop: done, budget, limit, or error? Then find the first wrong span. Not the last one, the first. Replay the run, with the recorded model responses or a scripted model, so you can reproduce it without paying for it or getting a different answer. Fix the boundary, not the prompt: a filter, a tool set, a limit, an order of steps. In the stale read: budget may only check a confirmed plan. And add a test so it stays fixed. Which leads to testing.

Test the wiring. Sample the behaviour.

Architecture tests

Who can call which tool? Is every risky tool gated? Does customer data reach a specialist?

Scripted model, every commit.

Behavioural evals

Does it find the cause? Does it respect a “no”? Is one agent still reliable enough?

Real model, many runs, pass rates.

How do you test something non-deterministic? Split the question. Architecture tests check the wiring: who can call which tool, is every risky tool gated, does personal data reach an agent that shouldn't see it. You don't need a real model for that. A scripted model is better: deterministic, offline, on every commit. My demo repo runs them on every commit. Behavioural evals check what the real model does: does it find the cause, does it respect a no. Run them many times and look at pass rates. And these evals answer the question from chapter one: does one agent still pass? None of this needs a specific framework. My demo uses Mastra, a TypeScript framework, because it has workflows, supervisors, memory, tracing and a local Studio in one package. Microsoft Agent Framework has the same building blocks for .NET: agents as functions, workflows with checkpoints, approval-required functions, OpenTelemetry, A2A and AG-UI hosting. That's the theory. The incident desk showed boundaries around one supervisor. Now back to chapter one: several specialists, and the question whether a network helps. The example: we're planning a developer conference, VibeKode 2027 in Mainz. 600 people, three tracks, a budget of 180,000 euros. Seven specialists with their own data and their own write tools. They run as A2A services. And it's ordinary planning software: the agents write into the plan, and every entry says who wrote it. Three parts. First, the same small question in three architectures. It touches three specialists only, venue, accessibility and budget, so the runs stay short. Second, travel for the four speakers from the US: passports, flights, hotels, and a booking that needs a person. I'll say no once. Third, we look for a bug in the trace. [DEMO, see cheat sheet. The network helped where the data was separate and cost where agents needed each other.

Let's put it together. [Compare runs tab: numbers from the runs you just saw, one run each, not a benchmark.] For the room question the single agent was fastest and complete. Centralized ran three specialists in parallel, but the Room C problem had to travel through the supervisor. Decentralized: venue asked accessibility directly, but budget read the board before venue had updated it. The blackboard weakness, found in the trace. For travel the picture turns. In the network only the travel agent ever saw a passport number, and the booking waited for a person. The single agent had to hold all of it. So the network helped where the data was really separate. It cost wherever the agents needed each other. Which is exactly what the research said. And the incident desk showed the other half: whatever the shape, the boundaries decide. Who sees what, who may do what, and who decides.

Use one agent as long as it passes your evals. When it doesn’t, split along context, capabilities, cost or clock. Everything else is a prompt conference.

  • Several specialists: pick the shape by who owns the answer.
  • Long tasks: a workflow around the agent, state in storage, memory by decision.
  • Risky tools: the smallest tool set, sorted by what it can break, filtered at every handoff.
  • People: an approval is a run that stops and a UI that shows the exact arguments.
  • And trace everything, so you can debug it and keep it fixed.
